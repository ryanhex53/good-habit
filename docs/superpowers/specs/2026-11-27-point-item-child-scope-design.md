## 0. 已由用户拍板的决策

| 决策点 | 结论 |
|---|---|
| 选择粒度 | **多选**。每个积分项可指定任意几个孩子；"所有孩子"是默认态；一旦指定具体孩子就进入"指定模式"，之后家庭里新增的孩子**不会**自动包含 |
| 编辑器形态 | **添加栏保持单行**（标题、分值），下方加一排孩子 chip；列表每行显示适用范围，并多一个 ghost 操作"适用孩子"，弹窗里是同一排 chip |

### 0.1 默认处理（我的提议，用户在同一次 check-in 里看到且未反对；批准时仍可推翻）

- 存量积分项一律视为"所有孩子"；新建默认也是"所有孩子"。
- 改适用范围**不影响已有流水**，只约束之后的登记。
- 登记页按当前选中的孩子过滤积分项；孩子端的得分指南只看到自己的；后端对不适用的登记返回 422。
- 只有一个（启用中的）孩子的家庭，不显示选择器与范围标签。

### 0.2 builder check 后补的裁量（我的，请一并核对）

- 停用孩子**不**级联清理任何积分项的范围；停用期间**保存过**的项会把该孩子从范围里去掉，**没动过**的项在孩子恢复启用后自动重新对其生效。
- 只剩一个启用中的孩子时，只要列表里存在任一指定模式的项，就照常显示范围标签与"适用孩子"按钮，避免出现登记页、指南、管理页三处都看不见、无处修复的死项。

## 1. 意图与背景

家里孩子一多，很多积分项天然只对一部分孩子成立："练琴"只属于学琴的那个，"帮忙照顾弟弟"只属于老大老二。现在系统里积分项是**纯家庭级**的：`reward_items` 只有 `family_id`，所有查询都是 `WHERE family_id=?`，`handleEarning` 只校验"这一项属于本家庭"，孩子端的 `/api/guide` 把全家积分项原样发给每个孩子。结果是家长登记时要在一堆不相干的项里找，孩子看到一堆自己永远拿不到的分，也没有任何机制阻止把"练琴"记给不学琴的孩子。

**成功的样子**：家长在新建或修改一个积分项时，几秒内就能圈定"给谁"；登记页切到哪个孩子，就只看到那个孩子能记的项；孩子登录后只看到自己的清单。

## 2. 目标 / 非目标 / 反目标

**目标**
1. 家长可给每个积分项设置适用孩子：所有孩子（默认）或任意子集。
2. 登记页只显示当前选中孩子可用的积分项。
3. 孩子端得分指南只显示该孩子可用的积分项。
4. 后端独立拒绝不适用的登记（422），不依赖前端过滤。
5. 管理列表能看到每一项的适用范围，并能就地修改。
6. 升级零成本：不需要任何手工迁移，所有存量项行为不变（对所有孩子生效）。

**非目标**
- 同一积分项对不同孩子分值不同。
- 每个孩子独立的积分项顺序。
- 奖品（prizes）按孩子区分。
- 追溯修改历史流水。
- 批量修改多个积分项的适用范围。
- 让"指定模式"的项随家庭新增孩子自动扩展（与用户拍板的语义相反）。

**反目标（做了就算失败）**
- "所有孩子"这一最常见情形变复杂：单孩子家庭多出任何控件；多孩子家庭在默认态要多点一下才能创建。
- 存量数据需要手工处理，或升级后行为有变化。
- 新增孩子后语义悄悄变化："指定模式"的项自动对新孩子生效，或"所有孩子"的项自动不再对新孩子生效。
- 前端过滤成为唯一防线（绕过 UI 就能把不适用项记给孩子）。
- 热路径多出磁盘查询：`handleEarning` / `handleGuide` 必须继续只读内存快照。

## 4. 产品行为

### 4.1 数据模型（我的裁量）

- 新增迁移 `migrations/0002_reward_item_children.sql`，建表：

  ```sql
  CREATE TABLE reward_item_children (
    reward_item_id INTEGER NOT NULL REFERENCES reward_items(id),
    child_id       INTEGER NOT NULL REFERENCES users(id),
    PRIMARY KEY (reward_item_id, child_id)
  );
  CREATE INDEX idx_reward_item_children_child ON reward_item_children(child_id);
  ```

- **语义：一个积分项没有任何关联行 = "所有孩子"；有 ≥1 行 = "指定模式"，恰好对这些孩子生效。** 不另加 `scope_all` 标志列——那会出现两份真相（标志说是"所有"，关联表却有行）。
- "指定模式但零个孩子"在这个模型里**不可表示**，这是有意的：UI 与 API 都不会产生空集（见 §4.7）。
- 存量项、`POST /api/bootstrap` 批量建的示例项、`internal/seed` 的种子项都不写关联行，天然就是"所有孩子"——这三处代码不需要改。
- **停用孩子不级联清理关联行**：`handleChildUpdate` 不改，迁移不加触发器或外键级联。原因：级联会把只指定了该孩子的项清成零行，而零行 = 所有孩子，语义会悄悄反转（§2 反目标）。

### 4.2 内存快照（我的裁量）

- `store.RewardItem` 增加 `ChildIDs []int64`；`nil`/空 = 所有孩子。
- `loadFamily` 增加一条查询，把本家庭**启用中**积分项的关联行一次取回并按项分组。
- 增加方法 `AppliesTo(childID int64) bool`：`len(ChildIDs)==0` 或包含该 id。
- 适用范围的增删改走现有的 `reloadFamily` → `ReloadFamily` → `loadFamily` 路径刷新快照，**不新增失效机制**。

### 4.3 API（我的裁量）

- `ItemView` 增加 `childIds`；"所有孩子"序列化为 `[]`（不要 `null`）。`GET /api/reward-items` 对启用与停用的项都要带 `childIds`（管理列表会显示停用项）。
- `POST /api/reward-items`：body 增加可选 `childIds?: number[]`；省略或 `[]` = 所有孩子。
- `PATCH /api/reward-items/{id}`：body 增加可选 `childIds?: number[]`；**省略 = 不动**，`[]` = 改为所有孩子，非空 = 恰好这些孩子。三种状态要能区分（Go 侧用 `*[]int64` 之类区分"没传"与"传了空"）。
- `handleEarning`：在快照里找到项之后、`applyLedger` 之前，`if !item.AppliesTo(body.ChildID)` → **422**，带稳定的错误码供前端展示；不写 ledger、余额不变。这一步在内存里完成。快照里找不到项的回库路径只处理"已停用"，不需要再查范围。
- `handleGuide`：按 `AppliesTo(sess.UserID)` 过滤后再返回。
- 校验 `childIds` 时每个 id 都必须是**本家庭、`role='child'`、`active=1`** 的用户；否则 422（与 `childOf` 同一口径）。跨家庭的积分项照旧 404。

### 4.4 家长端 · 积分项管理页（形态由用户拍板，细节为我的裁量）

- **添加栏**：标题、分值两个输入不变。下方加一排 chip：第一颗"所有孩子"，之后每个**启用中**的孩子一颗（只显示名字，不带余额数字）。默认"所有孩子"按下。
- **chip 交互**：点"所有孩子" → 清空具体选择、回到所有模式；点某个孩子 → 若当前是所有模式，切成指定模式且只选这一个；否则切换这个孩子的选中状态。**取消最后一个孩子的选中后，停在指定模式、零选中，"添加"按钮禁用**——不把空集悄悄当成"所有孩子"。创建成功后随标题、分值一起重置回"所有孩子"。
- **列表每行**：在主内容区显示范围标签——所有模式显示"所有孩子"，指定模式显示孩子名用"、"连接。名字从本家庭的孩子列表解析（用含停用孩子的完整列表，这样尚未重新保存过的项仍能显示已停用孩子的名字）。标签必须能截断（`min-w-0` + `truncate`，参见 `d8508eb`），不能撑破行。
- **"适用孩子" ghost 操作**：每行多一个按钮，打开弹窗：标题带积分项名，内容是同一排 chip，按钮"取消 / 保存"。"保存"在指定模式零选中时禁用；保存 → `PATCH {childIds}` → 更新列表 → 关闭。API 报错时沿用 `errMsg` 的展示方式并保持弹窗打开。
- **停用孩子与范围**：chip 只列启用中的孩子，所以保存只提交启用中的 id。停用期间**保存过**的项会把该孩子从范围里去掉；**没动过**的项保留原关联行，孩子恢复启用后自动重新对其生效。一句话：只有显式保存才改范围。
- **单孩子家庭**：添加栏的 chip 排在启用中的孩子 ≤ 1 个时隐藏（没得选）。每行的范围标签与"适用孩子"按钮的显示条件是：启用中的孩子 ≥ 2 个，**或**列表里存在任一指定模式的项。后者是为了防止死项——从多孩子变成单孩子（停用其一）后，范围不含剩下孩子的指定项在登记页、指南都不可见，管理页必须仍能看到它的标签并打开弹窗修复（此时弹窗里零选中、"保存"禁用，家长点"所有孩子"或勾上剩下的孩子即可）。范围里的孩子全部已停用时，标签要能看出来（如名字后加"（已停用）"，措辞留给 builder）。一项指定模式的项都没有、且启用中的孩子 ≤ 1 个时，页面与现在完全一致。
- **视觉**：chip 直接沿用登记页 `EarnView.vue:137-158` 的类（`btn rounded-full`，选中 `btn-primary`，未选 `btn-soft`，`aria-pressed`）。daisyUI 5 的 `[aria-pressed=true]` 会强制实心样式，这正是登记页依赖的行为，照抄即可，不要另造选中态。建议把 chip 排抽成一个组件，供添加栏与弹窗共用，避免两份切换逻辑。

### 4.5 家长端 · 登记页

- `activeItems` 在 `active` 之外再按 `childIds.length === 0 || childIds.includes(selected)` 过滤。
- 未选中孩子时不过滤（按钮本来就禁用）。
- 选中孩子没有任何可用项时，空状态文案要区分"还没建积分项"与"这个孩子暂无可登记的项"。只剩一个启用中的孩子、而现有指定项都不含他时，走的也是后一种，不需要第三种文案。

### 4.6 孩子端

- 无前端改动；`GET /api/guide` 由服务端过滤。

### 4.7 校验规则汇总

| 场景 | 结果 |
|---|---|
| 创建/修改时 `childIds` 含非本家庭、非孩子、已停用或不存在的 id | 422 |
| `PATCH` 省略 `childIds` | 范围不变 |
| 对不在该项范围内的孩子 `POST /api/earnings` | 422，不写 ledger，余额不变 |
| 停用孩子（无论范围） | 维持现状：`childOf` 拒绝登记；**不动任何积分项的范围** |
| 恢复启用孩子 | 停用期间没保存过的指定项自动重新对其生效；保存过的不会 |
| 停用一个积分项 | 维持现状：不出现在登记页与指南；其范围保留，重新启用后生效 |
